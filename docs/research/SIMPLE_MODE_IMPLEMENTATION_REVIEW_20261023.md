# 简单模式实施核查：可复用的成熟设计与草案修正

日期：2026-10-23。对照 `SIMPLE_MODE_SPEC.md` v0.1 的实施前建议。核对了下列官方文档，未运行所有候选框架或完成代码、许可审计。随后经用户授权完成的纵向路径见 [当前 SPEC](../specs/SIMPLE_MODE_SPEC.md) 和 [操作指南](../STRATEGY_WORKSPACE.md)，本文保留原建议与其依据。

## 结论

LM Studio 式体验可行。建议先做“简单界面 + 高级展开”，用同一份已解析的策略配置驱动检验、建议和纸面运行。首版无需三档界面、通用低代码平台或全量参数重写。

成熟产品已验证预设、配置校验、版本管理与运行监控的工程方式；它们不能替 TemperQ 证明投资效果。可运行性、经济增量、运行健康应分别给结论。

## 草案中应先修的六处

1. **固定仓位与风险偏好不相容。** 当前治理代码在固定方式下不使用 `target_volatility`。不能让用户选“稳健 10%”，后台却仍按固定仓位运行。选固定方式就展示仓位/现金与持仓规则；选 EWMA 或 ML 目标风险控制再展示目标值，并说明并非回撤上限。预设名称应描述实际行为，不能只有“稳健/进取”标签。
2. **默认值不能只写在一张表里。** 增加适用条件、来源类型、版本、是否已生效与覆盖记录。优先级建议：版本化工程默认 → 所选政策预设 → 用户显式覆盖 → 账户相关推导 → 交叉校验/冻结。账户推导不能静默覆盖用户已填的值，遇到不可行配置应说明冲突并要求修改。制度规则独立引用，不允许被这些层任意覆盖。
3. **锁定层需要拆开。** T+1、涨跌幅和法定税率属于按市场/日期适用的协议；佣金和最低佣金应允许填写实际券商口径；滑点是可调压力假设。预测期限和标签定义在当前信号版本内固定，未来改任务需新版本并重新检验。把所有费用或所有标签永久锁死都不合适。表单只读也不能代替后端校验。
4. **资金档位不是可成交保证。** 现有 `CAPITAL_TIERS` 用档位上限推导研究场景，并非对每个真实小账户验证过。需用实际现金、原始价格、板块最小申报量、费用和可卖数量做预检；金额过小不能仍承诺默认十只都能买到。日线成交额门槛不等于开盘流动性/冲击已被覆盖。
5. **三问保留，单一四灯改成独立状态。** “未发现已检查的问题”不等于证明无前视；未运行或无法核查的项必须单列。统计上不确定与没有运行故障可以同时成立。成绩卡不能把黄灯自动翻译成加仓、减仓等交易判断。
6. **里程碑改成先跑通一个纵向切片。** 官方模型尚未发布，治理前向账户尚未接入，公司行动仍限制长期回放；隐藏参数不能消除这些依赖。先用现有可用信号，贯通一个政策、一次检验和一个可验证的运行实例，再扩大目录与参数范围。

## 更小的实现结构

用户首页是“我的策略”。新建/修改时进入四步向导；策略运行后默认进入日常面板，显示最近数据日、最近建议日、账户记账日、下次任务和失败原因，不每天重新走向导。

底层保留五个职责：

- **信号规格**：固定模型/来源版本、输入与输出契约、数据要求、期限及可用时点。
- **政策预设**：持仓、调整节奏、风险方式与参数；可复用、分享，需检查适用条件。
- **策略版本**：绑定信号、政策、交易协议、成本口径和最终生效参数；经济行为修改生成新版本。
- **证据记录**：绑定该版本、数据快照、检验范围与结果；不与后续改过的配置混用。
- **运行实例**：绑定策略版本与账户，记录调度、心跳、失败和重试。改界面模式或通知设置不自动重置策略成绩；改变决策/交易时点则需重新识别版本。

配置处理顺序是“选预设 → 解析所有有效值与来源 → 校验 → 保存配置快照 → 同一快照用于检验/运行”。页面可以动态折叠，计算配置只有一份；后端拒绝非法覆盖，报告显示实际生效值、相对预设的修改与未生效字段。

参数元数据比草案再增加：`applies_when`、`unit`、`default_kind`、`default_version`、`resolved_from`、`requires`、`change_effect`。数值类型/范围沿用权威配置定义，布局与解释单独放 UI Schema。跨字段与市场可行性检查不可能仅靠增加一个注册字段自动完成；“所有新参数只改注册表”不宜作为验收承诺。

首版沿用 FastAPI、本地任务及现有成交引擎。项目已锁定 Pydantic，可先导出 Schema 并写轻量表单渲染；若以后工作台改成 React，再评估 JSON Forms。现有 `website/` 是独立 React 网站，不能因为它已有 React 就把本地工作台当成已经完成前后端重构。MLflow、Hydra、XState、Freqtrade 先借鉴机制，不一次性全部引入。

技术注意：JSON Schema 的 [`default` 是注解](https://json-schema.org/understanding-json-schema/reference/annotations)，验证器不会因此自动补齐字段；默认解析必须明确执行。Pydantic [默认不验证默认值](https://docs.pydantic.dev/latest/concepts/fields/#validate-default-values)，采用时需开启并验证交叉条件。已冻结运行版本不能被新版本默认值或环境变量静默改变。

## 成绩卡如何有结论，又不伪造确定性

| 面向用户的问题 | 可给的具体结论 | 仍须展示 |
| --- | --- | --- |
| 这套设置能运行吗？ | 已检查的必要条件通过 / 阻塞 / 未检查 | 数据覆盖、账户可行性、时点、公司行动与成本覆盖范围 |
| 这次修改带来了什么？ | 本段路径费用下降多少、换手变化多少；是否有优于指定基线的证据 | 对照版本、样本区间、敞口/风险差异、配对不确定性、尝试数与遗漏成本 |
| 它每天按计划工作吗？ | 按期完成 / 数据过期 / 任务失败 / 漏记 | 最近成功日期、缺失日期、重试与受阻；当前版本身份 |

经济效果不确定时，仍可在不夸大验证范围的前提下开始纸面观察。必要数据或账本能力缺失则属于运行阻塞。二者不能都叫黄灯。“目前有证据”只能指明确指标、对照和区间，不是对策略未来盈利的总裁决。

## 建议开发次序

1. 先选一个已可用信号，建立最小策略版本与最终配置快照；为这条路线登记必要参数，别先整理全部训练参数。
2. 做一个清楚说明行为的政策预设、简单/高级展开、依赖显示、实际账户可行性预检与“恢复预设/查看修改”。
3. 复用治理历史实验，统一显示三类状态；成绩卡只声明已经做过的检查。
4. 为该治理版本接通独立前向纸面运行；把数据新鲜度、失败/漏记及重试不重复记账作为验收。公司行动依赖未解决时明确阻塞，不能以漂亮曲线替代。
5. 普通用户独立走通后，再添加官方模型目录、外部适配与更多政策模板；ML 增量沿独立研究路线验证。

成功标准保留“普通用户可独立完成”，额外要求：用户能指出改了哪个参数、它何时生效、会怎样改变决策，并能区分能运行与收益已被证明。五分钟是待测的体验目标，不是当前已经达到的能力。
