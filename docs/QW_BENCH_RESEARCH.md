# QW 双 Bench：研究依据与首版设计建议

调研日期：2026-10-21。状态：设计建议，尚未实现、执行或测得 Bench 成绩。

本文核对了当前仓库代码、已生成报告、公开项目原始文档和部分论文元数据/摘要。公开项目的成绩是作者报告，不是本次复现结果。没有把所有相关论文全文读完，也不把以下清单当作穷尽检索。arXiv 检索工具对本次查询均返回空结果，补用了项目原始链接和 Crossref；GitHub API 后续触发限流，未取得引用仓库的提交哈希。

## 1. 结论：两套 Bench，共享一个评测内核

建议保留两个产品入口：

- **Model Check，面向用户**：给定模型、训练证据和任务，判断它是否可运行、评估是否有效、是否学到信号、是否具有扣成本后的增量。不能只返回一个没有限定含义的“训练成功”。
- **Platform Bench，面向平台开发**：在固定任务、数据和资源预算下，衡量平台能否更稳定地训练出达标模型，能否识别更多错误，以及安装、复现和运行效率是否改善。

两者共享任务定义、数据版本、预测格式、成本口径和评分器。平台端额外固定训练入口、预算、错误样本和运行环境。这样避免“用户报告一种算法，平台跑分另一种算法”。

原提案的“任务集 + 陷阱集 + 工程”可以保留，但平台端还缺一个主要结果：**默认工作流在相同预算下产出合格结果的能力**。只有防错率，无法说明一键训练平台的建模能力是否进步。

## 4. 用户端：给训练结果一张分层验收表

### 4.1 先分清两种使用方式

1. **用户任务验收**：用户的任务卡、股票池和预测期。回答这次训练是否达到预先约定的目标。非标准任务可以检查，但不能冒用标准 Bench 分数。
2. **标准任务评分**：模型满足固定任务和输入契约，具有未见过评测标签的证据，才参加标准任务比较。用户训练了一个完全不同的任务，不应强迫它去跑全部标准任务。

已训练模型不能自动获得干净的历史样本外测试。比如 2026 年训练且用过 2024-2025 标签的模型，不能再用同一历史段证明样本外有效；要用真实的折外预测和训练清单，或者模型冻结之后的新数据。历史滚动训练模型与固定权重模型也应分开标记。

### 4.2 建议输出五个维度

| 维度 | 验收证据 | 建议用户结论 |
|---|---|---|
| 可运行 | 安装、加载、输出 schema、有限数值、覆盖率、R1/R2 | 可运行 / 不可运行 / 未评估 |
| 评估有效性 | 时点契约、标签成熟、切分、预处理拟合范围、测试使用记录、预训练污染 | 通过已执行检查 / 存在违规 / 证据缺失 |
| 预测信号 | 主指标的置信区间、负对照、相对预定简单基准的差异 | 有信号 / 未达到门槛 / 证据不足 |
| 经济增量 | 固定组合下相对可实现基准的净收益差、区间、换手、成本压力测试、风险约束 | 达到经济门槛 / 未达到 / 证据不足 / 未评估 |
| 稳定性与增量 | 固定种子、时间窗口、市场状态、流动性层、风格暴露、官方模型对照 | 适用范围与薄弱区间 |

前两个维度决定后续数值能否用于标准验收；缺少来源证据不能被高 IC 抵消。经济维度也不能由 IC 推断。用户若只预注册了预测目标，应获得预测目标结论，经济检查作为单独结果。

“未达到门槛”和“证据不足”按预注册规则区分，例如置信区间整体落在门槛下方，或跨越门槛；不要只看 p 值。最低可检测效应、有效日期数和缺失覆盖都应展示。

### 4.3 最小任务集

首版使用两个任务家族成员：`cn_rank_5d`、`cn_rank_20d`。各自包含预测评价与固定多头组合评价；“多头”是将预测转为组合的一种评价层，不应伪装成额外独立预测任务来增加样本数。

- 固定历史股票池构造规则，包含当时存在而后退市的标的；全市场与高流动性子池作为预注册分层，避免规模和微盘暴露掩盖结果。
- 数据快照、交易日历、状态记录、复权处理、开平仓时点、滚动重训日程、缺失规则全部入 manifest。
- 同任务比较同一组 code/date；报告应要求固定最低覆盖率。模型缺失预测不能通过删掉难预测日期提高成绩。
- 低成本基准：随机/打乱负对照、反转、动量、低波动。监督学习基准：冻结的官方 LightGBM。简单因子不是保证单调增强的“阶梯”。
- 收益对照至少区分股票池等权参考、按相同交易约束和成本实现的参考组合、官方 LightGBM 组合。毛的等权参考不能称为可直接实现的净收益基准。
- 单个用户 LightGBM 不必显著胜过官方同配置 LightGBM 才算训练成功。只有声称超过官方基准时，才对该增量作正式检验。
- 行情状态与风格归因先作为固定诊断项，除非预注册为验收条件；不能要求每个短窗口都显著赚钱。

对整个期间事后标记上涨/下跌状态，可以用于解释，但不能把该标签作为当时模型输入。若用于训练策略切换，状态定义必须只依赖当时可得数据。

### 4.4 模型比较的统计协议

对于候选模型与冻结基准，在同日期计算差值：`d_t = metric(candidate, t) - metric(reference, t)`。保存日度 IC，以及同一记账频率下的收益和成本序列；现有只有汇总值的输出不足以完成配对比较。

使用按连续日期成块的 bootstrap 或预注册的 HAC 检验。每次重采样对全部模型、基准和种子使用同一组日期块，保留同日截面和模型之间的依赖。块长、重复次数、显著性、主指标和最低有意义改进量 `delta` 必须在看最终结果前确定；块长应考虑标签重叠与更长的依赖结构，不能盲定为预测天数。

- 差值区间下界高于 `delta`：有证据支持达到预定幅度的提升。
- 差值区间跨零：证据不足，不能写“无差异”。
- 要声称两版本近似等效，应预先定义等效界并执行等效检验。
- 要证明没有明显退步，应定义非劣界 `epsilon`，用差值区间下界与 `-epsilon` 比较；不显著不同不等于非劣。
- 主比较预注册；跨任务、多个基准或多轮候选选择要处理多重比较，例如固定检验家族的 Holm 校正，或针对策略候选集使用合适的 SPA 类方法。
- 三个训练种子不是三个独立市场，也不是用来把样本量扩大三倍。训练随机性与市场时间依赖分开报告。

避免把 5 日和 20 日、同一股票池的多个切片视为许多独立任务，从而获得虚高精度。只有两个相关任务家族时，应主要报告各自区间和敏感性，不夸大“跨任务普遍更好”。

## 5. 平台端：证明版本升级的四组证据

### 5.1 建模能力：固定预算下得到什么

固定机器/资源档位、数据、任务、重训日程和运行次数，比较 q-w 1.0、2.0 的默认工作流。计入特征计算、调参、失败重试和模型选择的时间；显式列出是否包含安装、下载、首次缓存。没有自动搜索的旧版也按同一预算上限执行。

建议同时保存两个对照：

- **固定配方回归**：相同模型与参数，检验升级是否无故改变预测、评分、成本或效率。
- **新版默认工作流比较**：允许新版使用更好的特征、模型或搜索，在相同预算上限下评价用户实际能得到的结果。

新配方得到提升与评分器修正得到分数变化是两件事。数据或评分器变化后，必须将旧版与新版在新协议下重新评估；不能把两套协议的分数直接比较。

主要报告：预测目标达标率、经济目标达标率、有效评估覆盖率、相对冻结基准的配对差异、到首个有效结果的时间、总训练成本。基础模型按训练模式/预训练证据分组。超时、崩溃和无输出计入端到端分母，不能静默删除。

这些率的分母写清“哪些任务 x 哪些重复运行”；它们是约定任务集上的观察结果，不自动代表所有新用户和市场的概率。若之后要声称“新手更容易成功”，还需要独立的用户操作实验。

### 5.2 防错能力：已知错误必须有独立答案

不要仅仅关闭一个检查再调用同一个函数，最后证明这个函数能找到自己预设的条件。每个案例都应包含干净对照、单一错误变体、独立定义的正确答案、被影响的阶段、预期的机器可读结果和允许的处理等级。

| 错误家族 | 具体案例 | 正确的可观测结果 | 证据边界 |
|---|---|---|---|
| 前视特征 | `shift(-1)`、中心窗口、全样本归一化、向后填补 | 定位错误并使标准验收失效 | 检查实际经过平台的特征路径；外部生成且来源不明的特征可能无法判定 |
| 时点修订 | 公告晚到、财务修订、ST 事后覆盖、未来复权事件 | 决策日前不可使用晚到版本；截断/扰动后历史预测不变 | 正确性依赖可用时间真实可靠 |
| 标签与切分 | 未成熟标签入训、股票行随机分割、预处理跨折拟合 | 明确拒绝违规训练或拒绝标准结论 | 随机切分并非所有任务都错；仅针对本 Bench 时间预测任务 |
| 股票池 | 删除后退市股票、使用当前成分回填历史 | 与独立历史名单核对后报错/降级 | 只有“已经删过的行情表”时，不能凭空识别缺失退市股票 |
| 交易记账 | 涨停买入、跌停减仓、停牌估值、现金、费用生效日 | 与手算金标准逐笔一致，或对缺证据部分拒绝经济验收 | 不强求一定弹警告；正确模拟无法成交也算正确处理 |
| 结果选择 | 重看测试、改门槛、仅提交最好种子、移动输出目录 | 本地可见范围内提示探索性/完整性问题；禁止冒充独立确认 | 本地台账不能证明未删实验，也不能发现平台外未申报搜索 |
| 数据损坏 | 重复键、错时区、交易单位错误、错列、缺快照 | 校验错误定位；不输出虚假的标准通过 | 有些异常只能标疑点，不能断言真实错误 |
| 执行与报告 | 缺成本依赖、关闭必要检查、加载失败、NaN 指标 | 对应维度未评估/失败；不被误报为通过 | “所有异常都报失败”不是准确检测 |
| 底座污染 | 预训练区间未知或覆盖测试期 | 污染风险未知/已知重叠，限制比较资格 | 时间元数据不足时应答未知，不能声称已排除污染 |

交易案例尤其需要独立金标准。例如不可卖出的持仓，其权重不能被再平衡算法通过等权重分配暗中减掉；缺失收益不能未经说明当作零；成本、现金和基准必须使用一致单位。先用极小面板手工验证，再测全市场。

评分至少分开：明确应阻断错误的识别率、应提示问题的识别率、干净案例的错误阻断率、故障定位准确率、评测覆盖率/弃权率。不能把“未知”“仅警告”和“拒绝”混成一个拦截分数。

固定公开严重错误案例要求零漏放、固定干净回归案例要求零错误阻断，可以作为确定性发布条件；对更广的随机变体要给出样本数与区间。有限样本的零误报不证明真实误报率为零；在独立二项抽样假设下，零事件的一侧 95% 上界约为 `3/n`，同源案例强相关时这个近似也不能直接套用。

首版可先做 **24 对案例**：前视 4、时点修订 4、标签/切分 4、交易记账 4、数据契约 4、台账/报告 4。每对都有干净与错误变体。数字是工程范围建议，不是基于实验选出的统计充分样本量。外部来源不可判定的案例另设“应弃权”组。

保留未公开的案例参数和组合变体，但公开规则家族。平台知道规则家族并认真实现正确行为是进步；只识别固定文件名、日期或案例 ID 才是无意义的刷分。

### 5.3 工程：用户能否实际得到同一个结果

固定 Windows CPU、Windows NVIDIA、Linux CPU 等明确档位；首版只认证实际测过的档位。测试干净环境安装、模型加载、示例推理、同快照评分、失败恢复。分别记录成功/总数、错误类型、墙钟时间、峰值内存/显存、预测容差。

R2 是同一权重的推理一致；R3 是同一预测与数据的报告重现；R4 是重训结果在声明容差/分布内重现。跨硬件不能笼统要求所有重训预测逐位相同。

小型合成案例进入 CI；真实快照的完整训练按发布周期运行。热缓存训练、冷启动完整流程、数据获取分开计时，重复运行报告分布，避免只展示最好一次。

### 5.4 报告是否忠实于证据

把“IC 显著、净收益不显著”“成本依赖缺失”“重看测试期”“检查未覆盖外部特征”等情况作为固定报告案例。评分器即使算对数字，若首页写出更强的成功结论，也算平台错误。

用结构化状态驱动 UI/Markdown，而不是让摘要文字自行推断。合成无信号数据上，检查长期重复试验的错误通过率是否符合设定水平；这类统计校准不应要求每次运行都不显著。负对照用来校准评价流程，不作为一个需要模型每次显著击败的随机赢家。

## 6. 如何发布“2.0 比 1.0 更好”

不建议推出一个能让运行速度抵消严重泄漏的总分。发布一个有共同任务 ID 的对照表，所有数字来自实际测量：

| 维度 | 1.0 | 2.0 | 判定依据 |
|---|---|---|---|
| 预测/经济目标达标数 | 待测 | 待测 | 固定分母和协议，分别列示 |
| 净增量与 IC 差异 | 待测 | 待测 | 配对差值、区间和预注册最小效应 |
| 严重错误漏放数 | 待测 | 待测 | 发布阻断项，旧案例不得回退 |
| 干净案例错误阻断数 | 待测 | 待测 | 固定对照及随机变体的样本数/区间 |
| 首次有效结果耗时 | 待测 | 待测 | 相同环境、预算与缓存状态 |
| 安装与 R1/R2/R3 | 待测 | 待测 | 环境矩阵及成功/总数 |
| 新增任务/适配器 | 待测 | 待测 | 单独报告覆盖扩展，不伪装成旧任务性能提升 |

“更好”可以是预测能力提高、固定效果所需预算减少、错误覆盖扩大、复现/安装改善。应说清是哪一种。若声称整体升级，则预先规定必须改进的主维度及其余维度的非劣边界，同时保留严重错误的硬约束。

平台版本和 Bench 版本分别编号，例如 `qwb 2.0 / qw-bench 1.0`。Bench 改规则时，应让两代平台重跑；保留固定历史锚点和新增滚动挑战两套结果，避免每年换卷后分数不可比。老版本无法完成新增任务时，标为不支持，并保留旧任务共同集合的比较。

## 7. 公平对照 AutoGluon 的方式

至少区分以下比较，回答不同问题：

1. **普通表格默认使用 vs q-w 默认工作流**：展示不懂金融验证的用户可能遇到什么风险。可以报告默认切分下的乐观偏差，但不能因此宣称 q-w 的学习算法更强。
2. **正确金融配置的 AutoGluon vs q-w**：统一时点特征、日期切分、训练期可用标签、预算、成本、组合和外部评分器。给 AutoGluon 合法的训练/验证配置；若所选预设启用内部 bagging/stacking，需另外核对其时序约束，必要时禁用并明确记录。
3. **q-w 旧版本 vs 新版本**：这是版本进步的主对照，比挑选一个外部默认设置更直接。

AutoGluon 是通用学习器，对 ST 历史缺失等问题未承诺自动校验。任务未覆盖的检查记“不适用/未提供”，不要把它算成 AutoGluon 的实现 bug。可以比较端到端默认使用的风险，但必须说明责任边界。

还可增加 Qlib 标准工作流作更接近领域的参考。不要把未经实际执行的外部比较写成已经证明的优势。

## 8. 测试集保密与前向证据

当前产品是本地训练，SPEC 明确分享站不接收预测、不计算收益。如果测试数据和评分逻辑都给用户，本地“保密测试集”就不具备强保密性。加密但在本地解密也不能解决这个约束。

首版可行方案：

- 公开开发区间和固定历史锚点；所有历史分数附训练与测试使用声明，明确是本地自查。
- 平台内部版本比较由评测流程隔离开发与保留集，记录每次访问；开发者可控数据的内部保留集仍依赖流程约束。
- 模型/配置先冻结，未来数据到达后顺序评价；尚未成熟的标签等待成熟。冻结后开始的前向阶段比反复使用已经看过的历史段更有说服力。
- 截至 2026-10-21，已被查看、试验或可能进入底座训练的 2026 数据，不能只因“还没公开”就自动成为干净保留集。前向评价从实际冻结时点后开始，不能追溯制造独立性。

真正独立的私有评分需要另外的受控评测方或服务，限制提交次数、记录冻结权重/代码、隐藏标签并保持审计。这会改变现有分享站边界，需要另立产品决定。离线提交预测或哈希可以约束部分事后修改，但本机时间戳、可删除台账和自报哈希不足以证明预测事先存在。

不建议首版就为排行榜、可信托管和在线收预测增加大量服务端工作。先把本地验收和平台内部发布评测做扎实，并如实标识证据等级。

## 9. 建议落地顺序与产物

以下是建议，不是已经存在的命令或目录。

1. **先修验收语义**：把 acceptance 变成可执行的结构化规则；拆开评估有效性、信号和经济结果；必要检查缺失时不产生相应标准通过；修正报告证据边界。
2. **分离评分内核**：接受规范预测表、任务 manifest 和训练/数据证据；统一生成逐期指标、持仓/成本序列和结构化结论。先验证简单规则与已知预测，再接用户模型。
3. **冻结 Bench 1.0**：两个预测期、简单基准和官方 LightGBM、快照与时间协议、选择预算、统计方案，保存当前平台的真实基线产物。
4. **先做 24 对错误/干净案例**：独立金标准、应阻断/应警告/应弃权等级与报告断言；在 CI 固定回归。增补来源不可判定案例，确保平台不会假装知道。
5. **加入版本比较**：从保存的逐期序列生成配对差值与非劣判定，运行完整训练和环境矩阵，发布 scorecard。
6. **再扩展**：更多市场、事件/概率任务、文本与基础模型污染、在线学习和前向记录；每个新任务需有相应任务卡与独立评价规则。

建议数据结构：

```text
benchmarks/
  qw_bench_v1.yaml          # 任务、快照、预算、指标、基准、统计、发布规则
  tasks/                   # 时间链、股票池、输入输出与重训协议
  cases/                   # 干净/错误案例、独立答案、预期处理等级
  references/              # 官方基准配置、摘要及可分发的小型金标准
src/qwb/bench/              # 后续实现的共享评分与比较入口
runs/bench/<protocol>/<platform>/<run>/
  manifest.json
  predictions.parquet
  daily_metrics.parquet
  portfolio_path.parquet
  case_results.json
  scorecard.json
  report.md
```

真实行情按授权保存在本地，只发布配方、内容哈希、环境信息与允许公开的结果。首版无需训练大型模型；最先应解决的是“同一证据能否得出同一、不过度的结论”。
