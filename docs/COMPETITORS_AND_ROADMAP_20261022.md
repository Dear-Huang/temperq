# 项目理解、竞品调研与优化路线

调研日期：2026-10-22。本文是代码与公开资料核验后的建议，不代表下述功能已经实现，也不替代 `bench/SPEC.md` 的评价协议。

同日实施补记：下文“现有项目”和优先级描述保留调研时状态。随后已实现本地训练后台 worker、独立历史版本、Bench 绑定、网页比较与白名单摘要导出；当前能力与操作以 [研究闭环说明](RESEARCH_WORKFLOW.md) 为准。MLflow、Optuna、DVC 和外部模型适配仍属于建议，未因调研而加入默认依赖。网站自动认证、完整训练预算评价和前向确认尚未实现。

进一步的训练质量增强、官方代码核对、成熟与前沿文献、真实开发对照及专业用户限制见 [专业研究链路审查](PROFESSIONAL_RESEARCH_AUDIT_20261022.md)。

## 1. 定位建议

Quant Workbench 可以聚焦为：**面向中文 A 股研究者、使用自备数据和算力、从 ML 训练到可复核评价与分享的研究工作台。**

“训练模型 + 回测 + 社区”已有成熟产品。当前更值得发展的方向是把数据时点、训练选择、模型版本、成本假设和评价证据贯通，让用户看清一次改动究竟改善了什么。这个方向是潜在差异点；还需要可复现案例与真实用户验证，不能视为已经建立的壁垒。

建议保留当前本地优先的架构：

```text
用户数据 / 本机或自有服务器
  -> 数据校验与快照
  -> 任务定义、滚动训练与模型版本
  -> 独立 Bench、研究账户与诊断
  -> 用户选择导出的证据包
  -> 网站展示固定版本、来源与评价范围
```

网站不需要在这一阶段承担训练、托管算力或执行陌生模型的职责。服务器部署网站与用户在自己的服务器训练，是两个独立的使用场景。

## 2. 现有项目做到了哪里

| 层面 | 从代码确认的能力 | 需要补齐的衔接 |
| --- | --- | --- |

| 训练 | 正式日频路径支持 LightGBM、Ridge，输出预测、指标、报告与最终模型 | Kronos 等实验适配尚未接入统一训练选择与配置 |

| 模型产物 | 配置、折、模型、预测和报告可落盘 | 成功重跑可替换同一输出目录中的文件，缺少贯穿各模块的不可变版本标识 |

| 推理 | 已有最新信号、目标持仓及参考股数输出 | 早期 SPEC 的首版边界与现在代码不一致，需要更新产品说明 |

| 项目 | 类型及已核验能力 | 对本项目的意义 |

| [RD-Agent](https://github.com/microsoft/RD-Agent) | 自动研发框架；基于 Qlib 的因子、模型及联合迭代工作流 | 可作为后期研究助理的参考；多数场景依赖 Docker、模型服务与代码执行环境，接入成本较高 |
| [Numerai](https://docs.numer.ai/numerai-tournament/scoring) | 预测提交与分轮评价体系；区分中间分和最终分、等待标签成熟、模型历史保留 | 借鉴前向提交与不可选择性重置的记录机制；其数据、目标与激励不适合直接套用到 A 股 |

聚宽与米筐也是应持续关注的国内候选。本次访问 [聚宽](https://www.joinquant.com/) 与 [米筐](https://www.ricequant.com/) 只获得页面外壳，部分文档受访问限制；因此不对其当前模型支持、价格、部署方式作细项判断。RQAlpha 仓库访问也未成功，不纳入本轮已核验能力比较。

不能仅凭项目 README 比较收益高低、防前视能力或实盘可靠性。要做这类比较，需要相同数据、股票池、交易约束、费用和训练预算的复现实验。

## 4. 工程组件选择

| 组件 | 建议 | 接入边界 |
| --- | --- | --- |
| [MLflow Tracking](https://mlflow.org/docs/latest/ml/tracking/) / [Registry](https://mlflow.org/docs/latest/ml/model-registry/) | 可选适配参数、指标、产物与模型版本，复用其查询/比较界面 | 当前只有规划，没有正式集成；本地运行不强制启动 MLflow 服务；金融时点、测试查看和 Bench 仍由本项目负责 |
| [Optuna](https://optuna.org/) | 在版本与评价链路稳定后接入参数搜索和剪枝 | trial 只看开发验证集；预先锁定次数、时间和资源预算；最终测试不参与搜索 |
| [DVC](https://doc.dvc.org/user-guide/data-management/remote-storage) | 当确有跨机器快照同步需要时，评估私有 S3/SSH 存储 | 不强制重写现有快照层；Git 仅保存元信息，行情与权重按授权留在私有存储 |
| Qlib / VeighNa Alpha | 先用小规模数据验证一条模型适配路径，再决定依赖范围 | 统一预测格式、时间语义、交易规则后比较；外部默认回测结果不能直接混入当前 Bench |

不建议一次把这些组件全部加入默认依赖。应记录版本、许可证与运行环境，并以一个真实工作流验证收益和维护成本。

## 5. 优先级与验收

### P0：统一研究记录和评价边界

建议建立几个职责明确的标识：

| 标识 | 表达什么 |
| --- | --- |
| `experiment_id` | 一个任务/研究问题，归集多个运行 |
| `run_id` | 一次训练尝试；失败、取消、同配置重试也分别记录 |
| `model_version` | 一份固定模型产物，与训练 run、配置、代码状态和数据身份关联 |
| `evaluation_id` | 一次评价，与预测哈希、协议、评分器版本、数据和模型关联 |
| `protocol_id` | 冻结的评价规则及其内容身份 |

这是建议契约，尚未实现。优先使用轻量 manifest 与现有产物，避免另造一套通用 MLOps 平台。模型名称和 `latest` 可以作为可变别名，不能替代固定版本。

验收：同名配置跑两次，两份结果均可追踪；UI/CLI 都能定位模型对应的配置和预测；Bench 结果能反查训练 run；分享模型卡能绑定固定模型版本与评价摘要。旧目录可只读导入并标记“历史导入”，不能补造当时缺失的记录。

同时更新能力矩阵，区分“已有代码、实验接入、规划”，统一 SPEC、README、网站和 Bench 的范围说明。

### P0：让评价适合指导迭代

当前 [`REAL_RUN_V0_4.md`](../bench/REAL_RUN_V0_4.md) 报告：

- 候选相对可实现等权年化净超额约 +412 bp，95% 区间约 [-1293, +2057] bp，跨零。
- 候选与低波动组合日收益相关约 0.81，尚不能证明超额已剔除风格。
- 当前净超额最小可检测差异约 2392 bp/年，无法据此判断小幅版本提升。
- 陷阱集完成首批 7 对，尚缺时点修订、时间/单位、随机切分等覆盖。
- 北交所部分陈旧估值/缺数原因仍待核实；退市股按最后价格保留，未模拟清算回收。

因此，应先把文档提出的信号配对差、成本、换手与拒单比较落实到 `bench compare`。净超额继续展示，但不将不确定的点估计包装成“新版更好”。比较前必须核验任务、时间窗、数据、协议与成交规则可比；不一致时说明原因。

验收：报告能给出“改善、变差、证据不足、不可比较”的清晰理由；缺数或陈旧估值不会被静默当成正常账户收益；新增陷阱同时包含错误案例与干净对照，报告覆盖范围。

### P1：把最常用的研究闭环做完整

工作台优先增加实验列表与比较视图，呈现任务、数据版本、状态、模型版本、Rank IC/配对差、区间、净超额、成本、换手、覆盖率和诊断。点击运行即可查看折、日志、配置与报告；从训练结果发起 Bench，再导出分享摘要。

网站上的评价来源建议区分“作者自报”与“提交的本地 Bench 证据”。哈希校验只能说明文件一致性，不能证明数据真实性、运行者身份或没有选择性提交。将来的平台复核必须有独立执行记录后才使用相应标记。

验收：用户无需复制多条命令即可完成“训练 -> 评价 -> 对比 -> 导出分享”；训练失败、Bench 未运行、证据缺失、协议不一致都有可见状态；不做跨协议的默认收益排名。

### P1：统一作业执行，保证服务器长任务可恢复

让 UI 与 CLI 调用同一个持久化 job 接口，由独立 worker 执行。先支持单机 CPU/GPU 资源声明、进程状态核对、日志、取消及重启后的任务处理；明确重试是重新计算还是从已校验的折恢复。

验收：关闭浏览器不影响任务；worker 意外结束后能检测中断；重试不覆盖旧 run；完成单元与对应配置/输入哈希一致时才复用。确有并发需求后再考虑队列服务，无需提前部署 Kubernetes 或分布式训练。

### P1：提高数据可迁移性与前向评价可信度

把数据/协议的稳定内容身份与机器上的物理路径分开，通过本机路径映射找到文件并重新校验。不能直接改历史协议路径、重算哈希后继续称作同一历史证据。

补齐北交所代码变更、停复牌、退市与来源单位的审计；选择有文档依据的处理规则。可以用第二套简化账户对照现金、费用、成交与持仓守恒，核查共享错误。

2024–2025 已反复用于开发，不能继续称为独立确认集。新确认集必须核实此前未查看；不能因为年份较新就认定未见。更稳妥的路径是预先冻结版本和协议，之后持续提交预测，等待目标成熟再评价，并保留全部轮次。

### P2：扩模型、调参与研究助理

统一 `fit/predict/save/load` 与能力声明后，再接 Qlib 的一条基线和 Kronos 等适配。比较运行时间、内存、预测质量及成本后的增量价值，再决定扩展模型库。

Optuna 和 Agent 的每次尝试都应生成 run，记录资源/费用、验证错误、搜索空间和选择理由。Agent 通过受控 job/config 接口调用研究流程；网站继续只读取元信息与可校验证据。若将来要执行生成代码或外部代码，再单独设计隔离 worker。

## 6. 推荐实施顺序

| 阶段 | 交付物 | 完成条件 |
| --- | --- | --- |
| A：研究记录贯通 | 能力矩阵、不可变 run/model/evaluation manifest、旧记录导入、UI/CLI 关联 | 两个模型版本均可从分享摘要追溯到固定产物与评价协议 |
| B：可比较与可恢复 | 实验对比、Bench 比较判定、持久化 worker、数据诊断补齐 | 长任务可处理重启；同协议比较说明不确定性；异常有来源与处理记录 |
| C：验证扩展价值 | 一个 Qlib 模型适配、可选 MLflow/Optuna、冻结后的前向记录 | 在固定预算与数据口径下，给出相对现有基线的增量证据 |

当前优先投入 A 与评价判定，不建议同时扩展多市场、券商实盘、托管 GPU、公开收益榜和大规模模型库。这样更符合现有非盈利、本地优先的定位，也能让后续网站展示建立在可追踪产物上。
